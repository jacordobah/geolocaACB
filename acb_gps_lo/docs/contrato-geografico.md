# Contrato geográfico Python → GPS

Go consulta la ruta geográfica al aprovisionar **a través del API Gateway**; no accede a MongoDB ni consulta Python por cada GPS. Configure `GPS_GATEWAY_BASE_URL` como origen HTTP(S) sin ruta y `GPS_GATEWAY_ROUTES_PATH` como ruta absoluta completa terminada en `/{route_id}`. El Gateway debe encaminarla a `GET /api/v1/routes/{route_id}` de Python, conservando cuerpo, errores y encabezados necesarios; el prefijo público concreto queda pendiente de acuerdo. `GPS_GATEWAY_ROUTES_TOKEN` es opcional y sólo se configura cuando se acuerde autenticación de servicio con Gateway. El identificador debe coincidir con `_id` devuelto. Timeouts y tamaño siguen limitados por `GPS_PATHS_HTTP_TIMEOUT` y `GPS_PATHS_MAX_RESPONSE_BYTES`. No hay fallback directo a Python.

**Contrato observado y consumido actualmente:** `_id`, `name`, `geometry:{"type":"LineString","coordinates":[[longitude,latitude],...]}`, `meeting_points` como lista ordenada de `{_id,name,kind:"meeting_point",description?,location:{type:"Point",coordinates:[lon,lat]}}`; opcionales `route_code`, `code`, `day_shift`, `endpoint_status`, `endpoint_reason`, `start_meeting_point_id`, `end_meeting_point_id`, `first_meeting_point_id` y metadatos `endpoints.start/end`. El cliente Go ya admite los campos `geometry_version` y `association_status` si Python los entrega, pero la respuesta real revisada no los aporta. `variant`, procedencia/confianza global de asociación y geometría explícita de extremos tampoco están garantizados.

**Niveles de aptitud:** una ruta es *consultable* si el JSON e IDs básicos se pueden leer; es *evaluable* si la LineString y puntos cumplen las restricciones geométricas de `internal/geo`; es *operativa* sólo si `OperationalReady` verifica además versión oficial no vacía, `association_status=verified`, `endpoint_status=resolved`, primer PE y extremos referenciados sin ambigüedad, y ausencia de asociaciones rotas. La huella local SHA-256 de geometría/asociaciones y `snapshot_hash` no son una versión oficial de Python. Una ruta con LineString válida y PE ordenados pero sin `geometry_version` y `association_status` es consultable/evaluable y **no** apta para crear una sesión real.

Cambio mínimo solicitado al propietario geográfico: publicar una versión oficial estable de geometría, estado global verificable de asociaciones y procedencia/confianza de PE; asegurar relación entre IDs geográficos y administrativos y semántica de variante si se usa. Deben mantenerse IDs de PE y orden, extremos explícitos y consistentes. El estado `endpoint_status=resolved` por sí solo no garantiza aptitud. GPS no inventará los campos faltantes ni relajará `OperationalReady`.

El motor aplica límites de geometría definidos en `internal/geo`: segmentos hasta 5 km, ruta hasta 100 km, latitud absoluta hasta 70°, sin cruce ambiguo del antimeridiano. El salto de aproximadamente 15,7 km pertenece a una geometría **sintética** de prueba y se rechaza explícitamente; la revisión 6.1 encontró compatibles las geometrías escolares reales examinadas. Las futuras rutas fuera de estos límites se rechazan hasta acordar una representación o método geodésico adecuado. La instantánea válida conserva geometría, PE, extremos, política y huellas durante la sesión, aun si Python cambia después.

## Respuesta completa requerida para `OperationalReady`

La responsabilidad del propietario geográfico es servir una ruta con identidad, LineString WGS84, PE ordenados y asociaciones verificadas; GPS consulta una sola vez al crear la sesión, valida y congela la instantánea. Ejemplo **contractual sintético** de respuesta que el cliente Go puede decodificar y que satisface las comprobaciones actuales de `OperationalReady` (Python real aún no suministra todos estos campos):

```http
GET /api/v1/routes/ruta-demo HTTP/1.1
Host: gateway.example.test
Accept: application/json
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"_id":"ruta-demo","name":"Ruta de prueba","route_code":"541","code":"541","day_shift":"morning","geometry_version":"rev-2026-11-02-1","association_status":"verified","geometry":{"type":"LineString","coordinates":[[-74.1000,4.6000],[-74.1010,4.6010]]},"meeting_points":[{"_id":"PE01","name":"Encuentro 1","kind":"meeting_point","description":"Ejemplo sintético","location":{"type":"Point","coordinates":[-74.1000,4.6000]}},{"_id":"PE02","name":"Encuentro 2","kind":"meeting_point","description":"Ejemplo sintético","location":{"type":"Point","coordinates":[-74.1010,4.6010]}}],"endpoint_status":"resolved","endpoint_reason":"verified_by_owner","first_meeting_point_id":"PE01","start_meeting_point_id":"PE01","end_meeting_point_id":"PE02","endpoints":{"start":{"source":"explicit","distance_m":0,"confidence":"high","matched_vertex_index":0},"end":{"source":"explicit","distance_m":0,"confidence":"high","matched_vertex_index":1}}}
```

**Obligatorios para decodificar:** `_id` igual al solicitado, `name`, `geometry.type=LineString` con al menos dos pares `[longitud,latitud]` válidos, y `meeting_points` como arreglo presente (puede estar vacío para una consulta básica). Cada PE requiere `_id` único, `name`, `kind=meeting_point` y `location.type=Point` con coordenadas válidas. **Adicionalmente obligatorios para `OperationalReady`:** al menos un PE, `geometry_version` oficial no vacía, `association_status=verified`, `endpoint_status=resolved`, y `first_meeting_point_id`, `start_meeting_point_id`, `end_meeting_point_id` presentes. Primero e inicio deben señalar el primer PE de la lista; si fin señala un PE de la lista, debe ser el último. El motor también exige límites matemáticos y una política de sesión válida. **Opcionales que Go consume:** `route_code`, `code`, `day_shift`, `description` de PE, `endpoint_reason`, `endpoints.start/end` con `source`, `distance_m`, `confidence`, `matched_vertex_index`. `variant` no está modelado por el cliente Go; una propiedad JSON con ese nombre se ignoraría, por lo que no debe considerarse resuelta.

El contrato Python real revisado no aporta `geometry_version` ni `association_status`; tampoco garantiza variante, procedencia/confianza **global** de asociaciones o geometría explícita de extremos. Los campos opcionales `endpoints.*.confidence` pueden existir, pero el guard actual **no exige ni verifica** su nivel; el requisito de confianza global debe acordarse con Python y luego revisarse en Go si se desea imponerlo. Además, Go admite que `end_meeting_point_id` no pertenezca a la lista de PE (podría representar un colegio), pero el JSON actual no tipa esa referencia: no puede demostrar por sí solo si es un extremo externo legítimo o una asociación rota. Este hueco exige acordar semántica/tipo del extremo y, si corresponde, reforzar la validación Go en un cambio posterior. `endpoint_status=resolved` solo es una declaración parcial del propietario y no reemplaza la autorización administrativa. Una huella SHA-256 calculada localmente y `snapshot_hash` no sustituyen una versión oficial.

**Incompatibilidad adicional por dirección:** el documento RF-09 de Python indica que las rutas 542 pueden iniciar en un colegio y terminar en el PE de mayor número; el guard actual de Go exige que `start_meeting_point_id` sea el primer PE de la lista. Aun si Python publicara versión y asociación verificadas, una ruta 542 con inicio en colegio podría seguir rechazándose. Es una decisión de modelo/validación pendiente entre GPS y propietario geográfico; no se corrige inventando un PE inicial ni relajando el guard en esta tarea documental.

**Ejemplo rechazado (aun con geometría calculable):** `{"_id":"ruta-demo","name":"Ruta heredada","geometry":{"type":"LineString","coordinates":[[-74.1,4.6],[-74.101,4.601]]},"meeting_points":[{"_id":"PE01","name":"Encuentro 1","kind":"meeting_point","location":{"type":"Point","coordinates":[-74.1,4.6]}}],"endpoint_status":"resolved","first_meeting_point_id":"PE01","start_meeting_point_id":"PE01","end_meeting_point_id":"PE01"}`. Se decodifica y puede evaluarse, pero `OperationalReady` la rechaza porque faltan `geometry_version` oficial y `association_status=verified`. No completar esos datos con valores inventados.

**Errores y reintentos:** 404 de Python significa ruta inexistente; 422/409 upstream indican identificador o dato geográfico inválido; 5xx, timeout y conexión fallida son indisponibilidad. Respuesta 200 con JSON inválido, ID distinto, LineString incorrecta, PE mal formado o cuerpo sobre `GPS_PATHS_MAX_RESPONSE_BYTES` se rechaza. GPS no transforma una respuesta inválida en ruta operativa; en el handler de control algunas fallas upstream se exponen como 503 y la falta de aptitud como 422. Reintentar indisponibilidad con espera y el mismo `Idempotency-Key` de creación; corregir datos inválidos con el propietario antes de un nuevo intento.

**Verificación:** usar `httptest` en `internal/pathshttp` y un fixture sintético que produzca el JSON anterior; después comprobar el endpoint Python real con una ruta vigente y `OperationalReady` sin modificar MongoDB. Validar que el ID coincide, la lista conserva orden, los extremos son consistentes y una edición posterior de Python no cambia la instantánea activa. No habilitar sesiones reales mientras falten versión/estado oficiales y autoridad administrativa.
